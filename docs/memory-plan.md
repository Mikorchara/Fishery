# 对话记忆（会话历史）实现计划 — memory-plan

> 状态：⏸ **暂缓**（2026-09-05 起草；2026-09-06 用户决定“会话历史以后再解决”，本计划留档备用，勿删）
> 目标读者：后续实现者（含 AI）。
> 背景速览：对话与报告已于 2026-09-05 切换为流式 + 默认关思考 + 输出档位可配（见 `docs/patches/2026-09-05_*`）。本计划为「让 AI 记住上文」的功能设计。

---

## 1. 为什么需要记忆（现状与痛点）

- **现状**：`stream_answer / ask_question` 是**无状态单轮**——每问都只发 `system + 最新一条 user`（内含当时注入的规则 + RAG + 问题）。AI 每次都是“第一次见你”。
- **痛点示例**：先问“鳗鲡最适水温是多少？”，再追问“那 32 度算偏高吗”——AI 不知道“那”指什么。
- **独立原型已验证可行性**：`scratch/llm_stream_proto.py --history-demo` 实测两轮追问，模型能正确接住“那”=水温；历史与知识库/RAG 注入**不冲突、可共存**。

---

## 2. 目标 / 非目标

**目标**
1. 单会话内让 AI 能引用上文（追问、指代、连续话题）。
2. 与现有能力共存：RAG 每轮照常注入最新知识、流式打字机不变、默认关思考不变。
3. 代价可控：不因记忆把上下文无限撑大 → 慢/贵（滑动窗口 + 上限裁剪）。

**非目标（本期不做）**
- 跨会话/长期个人记忆（用户画像、偏好）——那是后续话题。
- 让 AI “记住”它自己的思考过程（reasoning 不进历史）。
- 服务端持久化到磁盘（重启即清，先做内存版；若要落库再评估 SQLite，可沿用 `storage.py` 思路）。

---

## 3. 核心设计（回顾我们已讨论并验证过的结论）

### 3.1 记忆 = “回放拼好的原文”，而不是“重放纯净问题 + 每轮重注入”
- 每轮完成后，把**当时发出去的完整 user 消息**（含规则 + RAG）与 assistant 的**正式正文**存入历史。
- 好处：① 历史自带当时依据，无需对旧轮再查 RAG；② 与“每轮只对最新一问做 RAG”不冲突。
- 注意：assistant 只存 `content`（正文），**不存 reasoning_content**（思考不进上下文，避免污染与计费）。

### 3.2 一次请求的 messages 布局
```mermaid
flowchart LR
    A[system 人设] --> B[历史1 user:原文(当时规则+RAG)<br/>assistant:当时正文]
    B --> C[历史2 ... 最多 N 轮]
    C --> D[最新 user = 本次规则+RAG + 你这次的问题]
```
- 历史在 system 之后、最新一问之前，顺序保持。
- 只对**最新一问**做 RAG 检索注入。

### 3.3 长度代价与护栏
- 每轮历史都会吃输入 token（输入也计费，只是比输出便宜；思考已关，成本大头已解决）。
- 护栏：**滑动窗口 N=6~8 轮**（超过丢最旧）+ 可选的“历史总字符/总 token 上限”（如 4000 字，超出从最旧开始裁）。
- 每轮注入的 RAG 块已偏长（实测 5 块约 1.5k+ 字），窗口收紧能明显控成本。

## 4. 落点与文件（拟）

| 层 | 建议 | 说明 |
|---|---|---|
| 存储 | 新增 `core/conversation_memory.py` | 内存版：`dict[session_id] -> list[message]` + 锁 + 容量上限 + 滑动裁剪。纯逻辑、可单测（沿用 `llm_settings.py` 那种独立可测风格） |
| 会话 id | 前端生成一次 UUID，随请求带给后端 | 页面刷新可续（localStorage）；多标签 = 多会话 |
| 调用层 | `llm_advisor` 增加“接受历史”的入口 | 在 `stream_answer` 侧扩展（或新增 `stream_answer_ctx(question, sensor, history)`），保持非流式/无历史方法可用 |
| 路由 | `app.py` | `/chat_ai_stream` 增加 `session_id` 字段 → 读历史 → 调带历史方法 → 完成后把本轮(user原文, assistant正文) 写回 |
| 前端 | `templates/index.html` | 维护 `session_id`；发送时带上；无需其它 UI（会话级） |
| 诊断报告 | 本期可**不带历史** | 报告是一次性环境评估，带历史反而混淆；保持独立 |

## 5. 待决策点（实现前需拍板）

1. **历史是否含“规则诊断/RAG”整段**（回放原文，推荐）vs 历史只存“用户原始问题+正文”（简单，但旧轮依据丢失、追问质量略降）。→ 倾向回放原文。
2. **后端要不要记录“环境参考”**：每轮 user 都带当时传感器数值；若把历史原文回放，会固化旧传感器值。是否需要“最新轮覆盖”语义（可接受：历史就是当时快照）。
3. **裁剪粒度**：按轮数（6~8）？还是再叠加字数预算？→ 先轮数，字数预算做可调参数备用。
4. 是否需要**“记忆开关”按钮**（本轮可做可不做，ROADMAP 已把“思考做成可选项”单列，记忆开关同理可后置）。

## 7. 验收标准（Definition of Done）

- [ ] 同一 session 内追问（如“那 32 度呢”）能正确引用上文，不再答非所问。
- [ ] 历史只保留最近 N 轮；超长对话仍能工作且不显著变慢变贵（与无历史同量级感知）。
- [ ] reasoning 不进历史、不出现在回放；正文展示正常。
- [ ] 与流式打字机、诊断报告、多方案切换、默认关思考全部兼容。
- [ ] 存储层有本地单测；`py_compile`/离线自检通过。
- [ ] 补丁按 AGENTS 规范记录（before/after + CHANGES），troubleshooting 更新。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 历史使上下文膨胀 → 慢/贵 | 滑动窗口 + 轮数/字数预算；输入缓存命中前缀稳定可省钱 |
| 前端刷新丢 session / 多标签串话 | localStorage 存 id；每标签独立 id |
| 旧传感器/RAG 快照在历史里造成误导 | 回放原文即“当时现场”语义明确；必要时最新轮显式覆盖 |
| 与未来“思考可选项”叠加时的消息结构 | 统一在 `conversation_memory` 层保证只存 content，抽象清晰 |
| 重启丢记忆 | 接受（内存版）；如需落库单独评估 |
